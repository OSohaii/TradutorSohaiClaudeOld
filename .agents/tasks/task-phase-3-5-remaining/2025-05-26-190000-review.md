# Canonical types, pipeline planning, IndexedDB fonts, and canvas download rewrite

Six concerns bundled in one diff: a canonical `EngineId` type extracted to `types.ts`, a front-end `planPipeline` state machine, a cleaner-failure retry path in the pipeline hook, font storage migrated from localStorage to IndexedDB, per-engine token tracking, and a full rewrite of the canvas-based download renderer in `MangaViewer`.

The approach is additive — no existing APIs are removed, and the backend is untouched. The `planPipeline` function is informational only (the BFF still owns real planning); the cleaner fallback is a pragmatic try/catch retry; the IndexedDB migration is transparent to the rest of the app via Zustand's `StateStorage` abstraction.

**Watch for:** The canvas download always draws a white text-shadow regardless of the `showTextStroke` toggle, diverging from the DOM renderer (confirmed). The `setItem` implementation in the fonts IDB adapter clears and rewrites all fonts on every Zustand persist — a performance concern as the font library grows (confirmed). The `planPipeline` output is unused beyond a `console.debug` call, meaning it's dead code from a runtime perspective (confirmed).

## High-level view

`planPipeline` models the frontend's understanding of what the BFF will do but doesn't influence the actual API request. Its only consumer is a `console.debug` call — dead code from a runtime perspective, useful only as documentation of intent.

The cleaner-fallback logic retries without the Torii cleaner when the initial request throws an `ApiError` with `engine === 'torii'`. The `wantsCleaner` guard correctly prevents this retry when Torii is also the OCR/translate engine. The remaining edge case is a stale-closure race: if the user changes engine selection mid-flight, the retry decision uses values captured at call time rather than current store state.

Font storage moves to IndexedDB v2 with a `fonts` object store. Migration from legacy localStorage happens lazily on first `getItem`. The trade-off is a full clear-and-rewrite on every `setItem`, which works today but will degrade with many large font files.

The `handleDownload` rewrite handles rotation, scale, arc-based rounded rects, text alignment, and `textTransform`. It deviates from the DOM renderer in two ways: text-shadow is always drawn (DOM conditionally applies it based on `showTextStroke` and bubble type), and `letterSpacing` is not replicated (Canvas 2D has no native support).

The `Engine` and capability types (`OcrCapability`, `TranslateCapability`, `ImageOutCapability`) are declared in `types.ts` but have no consumers — forward declarations for a future engine registry.

## Canvas download vs DOM renderer fidelity

The `handleDownload` rewrite mirrors most of `BubbleOverlay`'s rendering: rotation via `ctx.save/translate/rotate`, scale-adjusted bounding boxes, `textTransform` for specific font families, per-bubble color, and text alignment. Two divergences remain:

**Text-shadow** — BubbleOverlay uses three modes:
- `enableTextStroke` true: `-1px -1px 0 #fff, 1px -1px 0 #fff, -1px 1px 0 #fff, 1px 1px 0 #fff` (strong stroke)
- `enableTextStroke` false AND (transparent OR sfx): `0px 0px 3px white, 0px 0px 3px white` (glow)
- `enableTextStroke` false AND normal bubble: `none`

The canvas code always draws the 4-offset pattern at 1px, matching only the "strong stroke" case. It never checks `showTextStroke` (local state accessible within `handleDownload`'s scope), and doesn't replicate the glow variant at all. Since `showTextStroke` defaults to `true`, most users won't notice — but anyone who toggled it off will get a different export than what they see on screen.

**letterSpacing** — BubbleOverlay sets `letterSpacing: ${letterSpacing}px` via CSS. Canvas 2D's `fillText` draws the entire string at once with no spacing control. Downloaded images with non-zero `letterSpacing` will have tighter text than the on-screen render.

## IndexedDB font persistence model

The migration path in `getItem` is well-structured: when IDB is empty, check localStorage for the legacy key, migrate fonts one-by-one, remove the legacy key, return the raw JSON so Zustand hydrates normally.

The concern is in `setItem`:

```typescript
setItem: async (_name: string, value: string): Promise<void> => {
  const parsed = JSON.parse(value);
  const fonts: StoredFont[] = parsed?.state?.customFonts || [];
  await clearAllFontsFromIDB();
  for (const f of fonts) {
    await saveFontToIDB(f);
  }
}
```

Every font addition or removal triggers a full clear-and-rewrite of all font blobs. Font data URLs are typically 100KB-2MB each. The `partialize` option limits writes to `{ customFonts }` changes, so this doesn't fire on unrelated state updates — but each `addFont` call still rewrites the entire collection. The sequential `saveFontToIDB` calls also create separate transactions per font; a single transaction with multiple `put` calls would be both faster and atomic.

## Cleaner-fallback stale-closure edge case

The retry logic reads `ocrEngine` and `transEngine` from store selectors at the top of the hook, then uses them in `runPipeline`. The `wantsCleaner` and `usingTorii` values are computed from these captured values. If the user changes engine selection in the UI while a pipeline call is in-flight, the retry decision uses stale values. This is a theoretical race (users don't typically change engines during translation), but the pattern of reading store state into closures without re-reading on retry is worth being aware of for future changes.
