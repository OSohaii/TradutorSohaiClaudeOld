# Canonical types, pipeline planning, IndexedDB fonts, and canvas download rewrite (v2)

Six concerns bundled in one diff: a canonical `EngineId` type extracted to `types.ts`, a front-end `planPipeline` state machine, a cleaner-failure retry path in the pipeline hook, font storage migrated from localStorage to IndexedDB, per-engine token tracking, and a full rewrite of the canvas-based download renderer in `MangaViewer`.

All five issues from the v1 review have been addressed. The canvas text-shadow now conditionally branches on `showTextStroke` with a glow path for transparent/SFX bubbles. The IDB clear-and-rewrite carries a comment acknowledging the trade-off. The `letterSpacing` limitation is documented inline. The `planPipeline` console.debug has a forward-looking comment. The engine/capability types are annotated as forward declarations.

**Watch for:** The cleaner-fallback retry still captures engine selectors via closure at hook render time, so a user changing engines mid-flight would cause the retry to use stale values (possible — unlikely in practice but the pattern is fragile for future changes).

**Verdict**: APPROVED

## High-level view

The canvas export now mirrors the three-branch text-shadow logic from BubbleOverlay: strong stroke when `showTextStroke` is on, a `shadowBlur`-based glow for transparent/SFX bubbles when stroke is off, and no shadow otherwise. The `letterSpacing` gap is documented as a Canvas 2D limitation.

The IDB font adapter's clear-and-rewrite is explicitly acknowledged as a pragmatic choice for the expected font count (< 10). The sequential `saveFontToIDB` calls still create separate transactions per font rather than batching in one transaction, but this is a performance nit rather than a correctness issue at current scale.

The `planPipeline` function is no longer dead code in spirit — the comment explains it's a debugging aid whose output will be surfaced in UI. The engine/capability forward declarations carry a comment explaining their future consumer.

## Stale-closure edge case in retry logic

The `runPipeline` closure reads `ocrEngine`, `transEngine`, and `useToriiForCleaning` from React hook selectors (evaluated at render time, not at call time). The retry path inside the `catch` block re-uses these same captured values to build the second request. If the user toggles engine selection in the UI during the first request's flight, the component re-renders with new selector values, but the in-flight closure still holds the old ones. This becomes a real concern only if future features allow queuing multiple images with different engine selections per batch, or if the retry logic grows more complex.
